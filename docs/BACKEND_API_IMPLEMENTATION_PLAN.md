# Rencana implementasi penuh backend API digaji.id

Status: roadmap aktif, 6 November 2026. Acuan utama: `full-docs/Spesifikasi API digaji.id — REST + WebSocket.md` (draft 4 November 2026), PRD v2.3, Matriks Menu/Role/Fungsional, Desain Database, dan keputusan Product Owner dalam percakapan. Proyek Go/Chi, Vue, dan MariaDB staging `192.168.11.85` dilanjutkan; migrasi `00001`–`00023` tidak ditulis ulang.

**Status implementasi:** migrasi aditif `00024`–`00037` sudah diterapkan pada staging. Inbox REST/WebSocket awal, CSRF untuk mutasi bersesi, `X-Request-Id`, versi akses/ETag, health/readiness, reauth 5 menit, sesi perangkat, preferensi, TOTP staf platform, dan token reset kata sandi sudah tersedia. Endpoint organisasi dan akses Admin baru memakai `{data,meta}` dan `snake_case` sambil mempertahankan alias lama. CRUD role kustom, penugasan role, Allow/Deny massal, scope, pengguna tenant, sesi, dan undangan staf platform sudah ditambahkan. SMTP lokal telah dikonfigurasi, tetapi host `digaji.id:587` tidak dapat dijangkau dan sertifikat host MX belum valid; pengiriman email menunggu perbaikan server mail. OpenAPI 0.17.0 mencakup master organisasi, geofence, lookup berscope, shift, pola, hari libur, roster draft/publikasi, shift instance, baca jadwal dan presensi ESS, serta izin kantor tambahan karyawan. Cakupan pasangan method/path tersedia di `API_ENDPOINT_COVERAGE.md`. Penulisan presensi, protokol WebSocket lengkap, worker outbox, dan modul domain lain masih mengikuti tahap di bawah.

**Pembaruan 7 November 2026:** CRUD keluarga dan kontak darurat, riwayat penugasan, kontrak draft/aktivasi/perpanjangan, endpoint baca pengajuan, serta editor alur approval (CRUD, tahap, default, simulasi) telah ditambahkan dan diuji di staging. Migrasi `00031` menyiapkan status `returned`, nomor percobaan, dan versi untuk kirim ulang pada request yang sama. Migrasi `00032` melengkapi izin approval untuk jadwal dan perubahan profil. Migrasi `00033` menyimpan catatan revisi per percobaan. Aksi `return` dan kirim ulang pada request yang sama telah diuji dengan versi, riwayat percobaan, task baru, audit, serta event outbox atomik. Kirim ulang saat ini menerima catatan perbaikan; perubahan field domain dan aksi `approve`/`reject` menunggu handler domain atomik. Perpanjangan menutup kontrak lama tepat sehari sebelum kontrak baru mulai.

**Pembaruan 8 November 2026:** keputusan `approve` bertahap dan akhir serta `reject` aktif untuk lembur, dengan `approved_minutes` terpisah dari usulan dan pembayaran. ESS dapat mengajukan lembur dan memperbaiki menit/alasan ketika request dikembalikan. Daftar dan detail lembur tersedia untuk ESS dan Admin sesuai scope. ESS juga dapat membatalkan pengajuan yang masih ditinjau atau dikembalikan; status tugas, request, instance, dan lembur berubah atomik. Migrasi `00034` menyimpan data aksi; `00035`–`00036` memberikan `lembur.buat` berscope diri sendiri kepada role KARYAWAN. Pengajuan domain selain lembur dan cuti menunggu handler return, resubmit, approve, reject, dan cancel.

**Pembaruan kasbon 8 November 2026:** migrasi `00040`–`00041` menambah kebijakan plafon/tenor per tenant, izin `kasbon.kelola`, indeks eksposur, riwayat waiver dan pelunasan. Dua belas operasi REST kasbon aktif untuk ESS dan Admin. Pinjaman tanpa bunga dibagi rata dalam satuan sen, sisa pembulatan pada cicilan terakhir. Plafon membatasi total outstanding aktif karyawan dan turut mereservasi pengajuan yang masih ditinjau/disetujui. Approval dan pengajuan ulang request yang sama telah terhubung. Pencairan butuh approval akhir dan reauth, menulis jadwal mulai bulan berikutnya sekali saja dengan referensi unik. Waiver mengurangi kewajiban; pelunasan penuh di luar payroll menutup semua cicilan pending dengan `settlement_ref` unik. **Integrasi potongan cicilan ke payroll belum dikerjakan**; tidak ada cicilan yang otomatis berstatus dibayar. Saat integrasi itu dibuat, payroll harus mengunci baris cicilan, memperbarui outstanding secara atomik, dan menghormati waiver/pelunasan agar tidak terjadi potongan ganda.

**Fondasi payroll 8 November 2026:** periode bulanan kini dapat dibuka oleh pemegang `penggajian.proses`, dibaca dengan `penggajian.lihat`, dan dicegah duplikat per tenant/bulan. Endpoint tambahan `GET /admin/payroll/periods/{id}/loan-deductions` menampilkan cicilan pending jatuh tempo hingga akhir periode dengan scope karyawan yang sama seperti akses payroll, termasuk cicilan tertunda dari bulan sebelumnya. Ini **pratinjau baca saja**; tidak membuat payroll run, tidak menautkan baris cicilan, dan tidak mengurangi outstanding. Waiver atau pelunasan langsung mengeluarkan cicilan dari pratinjau. Tahap berikutnya perlu kalkulasi payroll lengkap, validasi gaji cukup, reservasi cicilan pada draft, pelepasan reservasi saat recalculate/cancel, lalu posting tepat sekali ketika run final dan disetujui.

**Keputusan cicilan kurang dana:** bila sisa gaji bersih setelah potongan wajib tidak cukup, cicilan ditunda **seluruhnya** ke periode berikutnya. Tidak ada potongan sebagian. Cicilan berikutnya dari pinjaman yang sama juga ditunda sampai cicilan lebih awal dapat dibayar. `POST /admin/payroll/periods/{id}/loan-deductions/simulate` menjalankan aturan itu terhadap `available_net` masukan Finance Payroll dan memisahkan planned/deferred. Nilai masukan ini bukan hasil kalkulasi gaji server dan tidak boleh dipakai untuk posting. Saat kalkulasi payroll lengkap dibuat, algoritme yang sama harus menerima net hasil server dalam satu transaksi dengan reservasi cicilan; outstanding baru berkurang ketika run final.

**Komponen payroll:** migrasi `00042`–`00043` menambah status/versi komponen dan versi set komponen per karyawan. CRUD master serta GET/PUT penetapan karyawan sudah aktif. Jenis komponen dapat `earning`, `deduction`, atau `employer`; hanya `calc_type=fixed` yang dapat dibuat dan ditetapkan sampai kontrak persen/formula diputuskan. PUT mengganti seluruh set mulai `valid_from`, menutup set terdahulu sehari sebelumnya, menolak tanggal yang menyentuh payroll final atau bertabrakan dengan set masa depan, serta memakai reauth dan scope izin sensitif. Audit menyimpan versi/tanggal/jumlah komponen tanpa nominal. API ini belum menghitung gaji atau memposting cicilan.

**Keputusan prorata:** pembagi gaji tengah bulan adalah jumlah hari `day_type='shift'` pada roster **published** sepanjang periode; pembilang hanya hari shift di antara tanggal masuk dan tanggal akhir kerja, inklusif. `GET /admin/payroll/periods/{id}/proration?employee_id=...` memeriksa pembilang, pembagi, dan kelengkapan roster. Setiap tanggal periode harus memiliki roster terbit (termasuk tanggal sebelum mulai kerja) dan `join_date` karyawan harus terisi agar pratinjau menyatakan `ready=true`; tanpa itu kalkulasi draft harus menolak prorata. Helper nominal fixed membulatkan ke sen terdekat, setengah ke atas. Aturan komponen persen/formula masih belum aktif sesuai keputusan Product Owner.

**Aturan pajak/BPJS tenant:** Product Owner memilih editor PPh 21 terstruktur. `GET/POST /admin/payroll/rules/tax` menyimpan satu versi tenant untuk PTKP/status, rentang TER bulanan kategori A/B/C, dan tarif progresif tahunan; rentang memakai batas atas eksklusif dan harus tersambung tanpa celah. `GET/POST /admin/payroll/rules/bpjs` menyimpan tarif pekerja/pemberi kerja serta plafon upah per program. Publikasi memerlukan reauth, sumber aturan, dan audit; versi baru hanya boleh bertanggal setelah versi terakhir dan menutup versi sebelumnya secara atomik. Migrasi `00044` menambah sumber aturan BPJS. Struktur ini mengacu pada [PP 58/2023](https://peraturan.bpk.go.id/Details/274247) dan [PMK 168/2023](https://www.jdih.kemenkeu.go.id/dok/pmk-168-tahun-2023/summary). **Tidak ada angka tarif bawaan atau kalkulasi pajak yang aktif.** Sebelum menghitung draft, perlu validasi kelengkapan status PTKP karyawan, aturan yang berlaku sepanjang periode, rumus TER dan masa terakhir, serta tes pembanding terhadap contoh resmi.

## 2. Kesepakatan kontrak sebelum coding domain

1. Bekukan OpenAPI **spec-first** di `docs/openapi.yaml`: operasi, schema request/response, kode error, permission, scope, entitlement, reauth, idempotensi, dan contoh. Jangan memperluas file lama dengan endpoint kosong yang diklaim aktif; beri status per operasi (`planned`, `implemented`) dalam matriks terpisah.
2. Buat inventaris endpoint spesifikasi versus route nyata dengan `method + path` sebagai kunci. Setiap tiket implementasi menunjuk operasi OpenAPI, tabel, permission, halaman pemakai, dan tes penerimaan.
3. Pilih satu gaya kontrak baru (`snake_case`, `data/meta`, error berkode), pertahankan adapter route/DTO lama selama migrasi frontend. Contract test memastikan alias dan route baru memberi keputusan akses yang sama. Ubah frontend ke kontrak baru per fitur, baru deprekasi alias.
4. Tetapkan aturan umum: tenant dari sesi, `X-Request-Id`, `X-Access-Version`, cursor untuk log, offset untuk master, batas 100, waktu UTC, uang string desimal, `version` untuk edit serentak, `Idempotency-Key` untuk aksi bertanda I, audit untuk A, job untuk J, entitlement untuk E. Whitelist kolom sort/filter; validasi body dan batas ukuran per operasi.

## 5. Aturan WebSocket dan pekerja latar

- `GET /realtime/ws` memakai sesi cookie dan allowlist Origin. Koneksi diikat ke user, membership/tenant aktif, `access_version`, dan sesi perangkat; klien tidak memilih channel bebas.
- Dispatcher mengambil event dari outbox yang sudah commit, memeriksa ulang tenant, permission, scope, dan status sesi saat mengirim. Payload hanya ID, kategori, status, waktu, tautan yang akan dicek ulang oleh REST; tidak ada NIK/rekening/nominal/isi dokumen.
- `hello`/`resume` tidak dianggap jaminan penyimpanan event. `GET /notifications/sync?after_id=...` dan cursor inbox adalah jalur pemulihan; event boleh diterima lebih dari sekali dan UI menduplikasi berdasarkan ID.
- Revoke/logout/password change/terminasi/tenant suspend memutus koneksi terkait. Pembaruan akses menutup `4408`; sesi tidak sah `4401`; batas koneksi `4429`. Ping dan backoff mengikuti spesifikasi.
- Worker memakai claim/lease, retry dengan backoff, dead-letter yang dapat diaudit, dan idempotensi domain. Job ekspor membaca `scope_snapshot`; jika akses dicabut sebelum hasil diunduh, unduhan tetap diperiksa ulang.

## 6. Verifikasi dan rilis per tahap

- Tes kontrak OpenAPI untuk semua route aktif; tes integrasi MariaDB dua tenant, dua user role sama beda scope, Allow/Deny, entitlement, 403/404, ID lintas tenant, aksi serentak, replay idempotensi, dan perubahan akses saat sesi hidup.
- Tes domain untuk approval paralel, saldo cuti, presensi retry/shift lintas malam, payroll final, webhook replay, serta worker yang mati di tengah proses. Tes keamanan CSRF, Origin WebSocket, file URL, audit redaction, dan kunci tenant.
- Tes kinerja pada akses batch/login, daftar berscope, dashboard agregat, broadcast, dan koneksi WebSocket; angka batas laju/NFR final ditetapkan setelah beban nyata. Pantau p95, query lambat, antrean job/outbox, dan kegagalan delivery.
- Staging memakai migrasi aditif dengan backup dan uji restore. Rilis lewat perubahan backend yang kompatibel, migrasi frontend per fitur, baru penghentian alias lama. Modul preview berubah menjadi aktif hanya setelah endpoint, permission, tes, dan UI end-to-end selesai.

## 8. Irisan implementasi pertama setelah rencana disepakati

1. Tambah matriks `method + path` dari spesifikasi API ke dokumen kontrak, tandai `active`, `alias`, atau `planned`; koreksi Bagian 11.1 untuk pajak/BPJS per tenant dan tambah operasi pola roster yang belum ada di spesifikasi.
